Plan correction · R1

steps is not a game field

It counts the harness's polling loops and jitters run to run on unchanged code. Parity ignores it; "the bot made the same decisions" is proven by the trace diff instead.

Plan correction · R1

The engine is checked against a manifest

Phase 8c changed three rules modules by design, so the engine is not byte-identical to v2. T2 checks all 19 against a sha256 manifest taken at Step 0, and cmps the other 16 against v2.

Left open · R5

A load mid-card

Resolve's card and hold timers and FX timers are not reset on load, so a load in the middle of a card could still let a pending callback fire. Never reproduced.

Why bother

What the review found

Bug 12 · fixed in Step 7

Ground items vanish on save and load

groundItems is not in the save and is neither restored nor cleared on load. A weapon dropped by a wound is gone after a reload, and a later load or lesson keeps the previous game's items.

Bug 13 · fixed in Step 7

In-flight state survives a load

pendingContact, pendingSteps, walking and four others keep their values across a load. The first to test live is a load right after a contact.

Finding 15 · fixed in Step 8

v2 and v3 share one save list

Under file:// both read ambush-mission1-saves-v1, so a v3 save can be loaded into v2 and the other way round.

Dead code · Step 1

About 290 lines nothing reaches

43 unused debug hooks, the one-entry presentation chooser with its 16 guards, v1's dice tray, an empty path layer, two dead aliases, four dead CSS classes.

Duplication · Steps 2, 4, 5

The to-hit card is written five times

Five chains repeat the hit test 17 times and the landing effect 13 times. Counters are built in four places. One toHitCard and one counter builder replace them.

Seam · Step 10

Legality is read back from the DOM

The bot and the stack panel read button disabled, and refusal reasons are written apart from the tests, so they can disagree. One verbs(s) → {ok, why, cite} feeds them all.

Method

Three stages, each proven by parity

A

Cut, no renames

Code moves byte for byte into 13 plain scripts in the original order. Only the IIFE's first and last lines go. A script checks that the 13 files joined equal the old body.

Step 3 · session R3
B

State onto one object

13 variables move to M1.state, exactly what the save writes. That fixes bug 12 by construction; a reset() per chain fixes bug 13. Old saves still load.

Steps 6–7 · session R5
C

Namespace, file by file

Each file wraps in an IIFE and exports through AmbushM1, leaf files first. At the end window holds three globals from these files.

Proof

How each step is checked

T1 quick · after every step and sub-step ~4 min
  • node --check on each changed file
  • the 17 engine suites (guard against an accidental engine edit)
  • bot parity, seeds 7000–7005, Normal and Easy
  • trace diff of seed 7000, both difficulties
T2 full · end of each session ~20 min
  • everything in T1
  • bot parity 30/30 Normal and 30/30 Easy
  • the five live_*.py drives, zero console errors
  • cmp of the 19 rules modules against v2

"Identical" means every field of each run record matches except seconds: outcome, VP, rounds, activations, casualties, exits, console errors and, most telling, steps, the number of decisions the bot made. The trace diff catches a game that drifts mid-way and still ends on the same totals.

Stop rules

When to stop

Any difference: roll back

A T1 difference stops the step. Roll back with git, find the cause, redo the step. Never patch forward.

Behaviour changes are approved first

Steps 7, 8 and any wording in Step 10 are listed before they run and approved by Wan. Afterwards only the baselines they change are re-recorded.

The engine stays byte-identical

No step edits the 19 rules modules or ambushdialogs.js. T2 checks this with cmp.

Done means

mission1.js gone; 13 files; three globals; one d10; AmbushMission, the bot, lessons and live checks unchanged; bugs 12 and 13 fixed and covered by a live check.
